# Teaching overhaul — design

Date: 2026-08-25
Status: approved, ready to implement

## Problem

The brief reads well but does not teach. The student reported four distinct failures:

1. Jargon is used without explanation (NOI, absorption, CMBS, capital stack).
2. Reading it once does not make it stick — comprehension in the moment, no recall later.
3. The writing assumes a finance background the reader does not have.
4. It is passive. There is nothing to do but read and close it.

The root cause of (2) and (4) is the same: the brief tells without ever asking. Retrieval —
being asked before being told — is what converts reading into recall.

Time budget: about ten minutes, sitting down. There is room for real teaching.

## Design

### 1. Teaching voice

Three rules enforced in the prompt:

- **Gloss on first use.** Any term of art appearing anywhere in the brief gets a plain-English
  clause where it appears. No unexplained acronyms.
- **Analogy before mechanism.** Each concept opens with an everyday comparison, then the CRE
  version tied to a real number from that morning.
- **Zero assumed vocabulary.** Write for a smart reader with no finance background.

### 2. Retrieval structure

The concept section becomes three beats:

- **Today's concept** — analogy, then the mechanism worked against that morning's real numbers.
- **Check yourself** — one question on what was just taught, answer hidden.
- **Review** — one or two questions on concepts learned earlier, answers hidden.

Questions are generated fresh each run rather than stored. Varied phrasing is better retrieval
practice than a memorized question, and it keeps the state file small.

### 3. Spaced repetition

`state/log.json` gains a `schedule` list. Each entry tracks one concept:

```json
{"concept": "Cap rate", "taught_at": 1, "due_at": 2, "stage": 0}
```

Review intervals by stage: **1, 4, 14** briefs. After the final stage the concept graduates and
is removed from the schedule.

Scheduling is by brief count, not calendar date. If runs are missed, reviews do not avalanche
into a single pile — the sequence resumes where it left off.

At most two reviews per brief, chosen oldest-due-first, so a backlog drains steadily instead of
flooding one morning.

**Backward compatibility:** a missing `schedule` key reads as an empty list. The existing
`log.json` keeps working and simply produces no reviews on its first run. This follows the
standing rule in `CLAUDE.md`: a missing key should degrade, not crash.

### 4. Tap-to-reveal, without weakening escaping

`render_html()` escapes all HTML deliberately — that is what stops a hostile or malformed
headline from injecting markup into the published page. That property must not be relaxed.

Therefore the model never emits HTML. It emits a plain-text marker:

```
> ANSWER: the answer text
```

`render_html()` recognizes the marker and constructs the `<details>` element itself. Model output
stays fully escaped; the interactive element is generated by our own code from a trusted template.

CSS is added so the element reads as a tappable control on a phone.

### 5. Notification

`make_teaser()` in `deliver/push.py` currently sends numbers, concept name, and the action item.
It gains the **review question without its answer**. A question on the lock screen is retrieval
practice before the page is even opened; the answer requires opening the brief.

## Files

| File | Change |
|---|---|
| `brief/generate.py` | `build_prompt` (voice, retrieval sections), `main()` (schedule read/write), `render_html` (details marker + CSS) |
| `deliver/push.py` | `make_teaser` carries the review question |

| `state/curriculum.md` | worked example updated to model the plainer voice |

## Verification

- `python brief/generate.py --dry-run` prints the assembled prompt with no API call and no cost.
  Seeded `log.json` fixtures confirm review selection picks the right concepts at the right
  brief numbers.
- Scheduler state transitions tested directly against a temporary log: new concept enters at
  stage 0, a reviewed concept advances, a concept past the final stage graduates out.
- `render_html()` verified to escape hostile input while still producing the `details` element
  from the trusted marker.
- Only after local verification passes does a live run spend API credit.

## Explicitly out of scope

A full JavaScript app — flashcards, scoring, progress dashboard — was considered and rejected for
now. It is substantial scaffolding around the same underlying content. The `schedule` data model
designed here is what such an app would be built on later if wanted.
